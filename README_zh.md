# Chem324 中文对照版 — 维护说明

本仓库是 [DPotoyan/Chem324](https://github.com/DPotoyan/Chem324)（Iowa State
Chem 3240 量子化学讲义）的**中英对照版**。

- 英文原文**逐字节保留**，中文以可折叠块插入在每一段、每个列表之后。
- 只翻译**大段自然语言**：标题、代码注释、公式、表格一律保持英文。
- 原书中的**错误**以可见的 `原文勘误` 卡片标注，不改动原文。

线上地址：<https://julianshi.github.io/Chem324/>

---

## 一、维护方式：点一下按钮

日常维护只有一步：

1. 打开 <https://github.com/julianShi/Chem324>，点 **Sync fork → Update branch**。
2. 同步后 GitHub Actions 自动运行，新增/改动的段落被翻译，站点重建并发布。

你什么都不用装、不用跑。同步进来的英文改动会被翻译；没改动的段落走缓存，**不花时间也不花 token**。

## 二、脚本原理

`scripts/translate.py` 把整个流程拆成互相独立、可单独运行的四个阶段：

```
slice      把每页 Markdown 切成"结构片段"与"可译段落"
translate  只为缓存里没有的段落调用模型
apply      把译文按可折叠块插回 Markdown（英文保持原样）
stats      覆盖率报告
all        依次执行上面四步
```

`.github/workflows/deploy.yml` 在**上游原有的构建流程里插入两步**（生成译本、提交缓存），
其余构建/发布逻辑完全沿用上游——因为上游的构建要执行 pyscf notebook、启动 Jupyter
服务器、渲染 marimo 与 Quarto 幻灯片，重写一份很容易与上游脱节。

### 为什么不做"逐句直接翻译文件"

因为 Markdown 语法比散文脆弱。公式、`:::` 指令、代码围栏、链接目标一旦被模型改动，
页面会静默损坏——在 diff 里看不出来，只在浏览器里才暴露。所以：

**结构性内容从不经过模型。** 切片器把文件拆成"字面量"和"段落"两类，模型只看得到段落。
公式、指令、代码、选项行是以字面量身份原样拼回去的，模型没有机会改坏它们。

### 缓存为什么按"原文文本"索引

缓存文件 `translation/zh-cache.json` 是 `英文段落 → 中文译文` 的映射，键就是英文原文本身。

- 段落没变 → 命中缓存，零成本；
- 段落被作者改了 → 未命中，只重译这一段；
- 段落被删了 → 留下无害的孤儿条目。

**不能**按行号或片段编号索引：作者只要插入一段，后面所有编号就会平移，缓存会整体错位——
译文会被贴到错误的段落下。上一版人工翻译重切片时就踩过这个坑，627 段靠"原文文本"重新
对齐，0 段落丢失。

缓存是纯文本、可读、可 diff、可回滚，跟源码一样审阅。

## 三、两道校验，以及它们各自证明了什么

**第一道：英文是否被改动过？**

`apply` 会把自己插入的每一段记录到旁挂文件，`verify --strip-interleaved` 按**内容本体**
（不是正则）把这些插入删掉，剩下的必须与原文件**逐字节相同**。

报告里 `0 containing CJK` 这个数字是关键：删掉插入后一个中文字符都不剩，才证明英文真的
没被动过。

> 注意这道门禁**证明不了**译文质量，也证明不了插入位置是否合法——插在公式中间时它照样
> 全绿（因为删掉插入后原文完好）。所以还需要第二道。

**第二道：译文本身是否破坏了标记？**

逐段比对原文与译文的 `**`、`$...$`、链接目标的多重集是否一致。这一道抓出过真实事故：
某个模型把 41/133 段的 `**` 全删了（中文读起来完全通顺，只有计数能发现）。

**第三道（构建后）：页面是否真的渲染正确？**

所有源码级检查都对、页面却依然烂掉的情况是存在的：`mystmd` 里**冒号围栏不能可靠嵌套**。
在 `:::{grid-item-card}` 里插入 `::::::{admonition}` 会当作纯文本泄漏，并且提前关闭外层
note，**静默吞掉下一个标题**。所以插入块一律使用**反引号围栏**。

因此发布前会用 `myst build --html` 真正构建一次，并检查：渲染出的中文块数量是否等于插入数量、
有没有围栏字符串泄漏、转换区域后面的标题是否还在。

## 四、翻译规则（刻意只有两条）

1. **跳过表格** —— 单元格是短语，中英混排的表格比纯英文更难读；
2. **跳过不足 8 个词的段落** —— 碎片不值得翻译。

其余全部由**结构**保证：标题、代码、公式、指令选项在切片阶段就被划为字面量，
根本不会送到模型面前，不需要任何"类型清单"去维护。

想调整：`scripts/translate.py` 里的 `MIN_WORDS`，或 `--translate-tables` 打开表格翻译。

---

## 五、手动修正某一段译文

直接在 `translation/zh-cache.json` 里改对应条目即可（键是英文原文），提交后下次构建生效。
不需要重新翻译任何东西。

## 六、一次性设置（第一次使用才需要）

### 1. 打开 GitHub Pages

本仓库的 Pages **目前还没有开启**（API token 没有 `pages` 权限，必须手动开）：

**Settings → Pages → Source: `Deploy from a branch` → Branch: `gh-pages` / `(root)` → Save**

`gh-pages` 分支由 Action 在第一次构建时自动创建。开启后站点出现在
<https://julianshi.github.io/Chem324/>。

### 2. 配置翻译用的 key

| 位置 | 变量 | 必填 | 说明 |
| --- | --- | --- | --- |
| Secrets | `OPENROUTER_API_KEY` | **是** | <https://openrouter.ai/keys> 的 key |
| Variables | `OPENROUTER_BASE_URL` | 否 | 默认 `https://openrouter.ai/api/v1` |
| Variables | `OPENROUTER_MODEL` | 否 | 默认 `nemotron-3-ultra-550b-a55b:free` |
| Variables | `TRANSLATE_LIMIT` | 否 | 每次运行最多新译段落数，默认 1200 |

> **注意：OpenCode zen 的 key 不能用在这里。** 实测 zen 的免费模型（含
> `nemotron-3-ultra-free`）会返回 `403 FreeTierError: OpenCode's free tier can only
> be used from within OpenCode`——免费档被限制只能在 OpenCode 客户端内调用，CI 一律 403。
> 因此本仓库使用 **OpenRouter** 的 key。仓库里原有的 `OPENAI_*` secret/变量是 zen 的，
> 请另行添加 `OPENROUTER_API_KEY` 这个 secret。

**关于推理开关**：该模型默认会为一句短句消耗数千 reasoning token，实测 8 段要 54 秒。
脚本默认发送 `reasoning: {enabled: false}`，同样 8 段降到 6 秒（**约 9 倍**），
且标记保留率仍为 8/8。要保留推理用 `--keep-reasoning`。

## 七、已知限制

- **图内的英文文字不会被翻译。** 结构化流水线只保证 Markdown 语法的完整，图片里的标签
  仍然是英文。这是目前最大的缺口。
- 门禁证明"语法没坏"，**不证明"意思对"**。译文质量问题仍需人工抽查。
- 同步 fork 若与上游在 `deploy.yml` 的同一位置发生冲突，需要手动解决一次。
